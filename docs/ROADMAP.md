# BPMN Studio — дорожная карта

> Рабочее название продукта: **BPMN Studio**.
> Позиционирование: «среднее между Bizagi Modeler и StormBPM» — визуально богатый редактор
> процессов + исполняемая семантика (проверки, прогон токена) + совместная работа.

**Версия документа:** 0.1 · **Дата:** 12.11.2026 · **Статус проекта:** планирование

---

## 0. Легенда статусов

Во всех этапах задачи размечены чекбоксами. Меняем только символ, текст задачи не трогаем —
так история правок остаётся читаемой в `git diff`.

## 1. Стек: что делаем на Python, а что нет

> **Решения, принятые 12.11.2026 (закрывают развилки перед стартом):**
> - **Форма поставки — веб-приложение.** Обоснование в §1.5. Десктоп-оболочка (Tauri) —
>   опция этапа 6, а не отдельная кодовая база.
> - **Ядро редактора — bpmn-js** + собственные модули (стили, комментарии, оверлей токена).
> - **Порядок после этапа 1: валидация → симуляция** (этапы 2 и 3, как в §3).

### 1.1. Короткий ответ

**Python — да, но не на 100%.** Python идеален для того, что составляет *мозг* продукта:

- парсинг/сериализация BPMN 2.0 XML и валидация по XSD;
- графовый анализ схемы и движок проверок;
- интерпретатор токена (исполнение процесса);
- backend: API, хранение, версии, права, экспорт, совместная работа;
- тесты, генерация документов, CLI.

И **плохо подходит** для *холста*: интерактивный редактор диаграмм — это тысячи
SVG-узлов, hit-testing, drag с 60 fps и тонкая работа с DOM. На Python это делается
либо через Qt (PySide6 — рабочий, но десктопный путь), либо не делается хорошо.

### 1.2. Рекомендуемая архитектура: веб, Python-backend, TS-фронтенд

```
┌──────────────────────────── Браузер ────────────────────────────┐
│  React + TypeScript                                              │
│  ├─ bpmn-js (ядро редактора: рендер, палитра, ручки, undo)       │
│  ├─ модули расширения: цвета/стили, комментарии, оверлей токена  │
│  └─ инспектор свойств, панель проблем, панель симуляции          │
└───────────────▲──────────────────────────────┬──────────────────┘
                │ REST (JSON, BPMN XML)        │ WebSocket
┌───────────────┴──────────────────────────────▼──────────────────┐
│  Python 3.12 · FastAPI · Pydantic v2                             │
│  ├─ diagrams / versions / comments / permissions (CRUD)         │
│  ├─ validation: XSD + правила графа (networkx)                  │
│  ├─ simulation: интерпретатор токена, история, счётчики         │
│  ├─ export: SVG / PNG / PDF / DOCX / CSV (headless Chromium)    │
│  └─ collab: presence, CRDT-синхронизация, pub/sub               │
├─────────────────────────────────────────────────────────────────┤
│  PostgreSQL · Redis · S3-совместимое хранилище (MinIO)          │
└─────────────────────────────────────────────────────────────────┘
```

Почему так:
- **bpmn-js** (MIT, Camunda) уже даёт 70% «рисовалки» уровня Bizagi: палитра, лейны,
  ручки ресайза, ортогональная маршрутизация, undo/redo, валидный BPMN 2.0 XML на выходе.
  Писать это с нуля — 3–4 месяца и всё равно хуже.
- **bpmn-js-token-simulation** (тоже MIT) закрывает половину этапа 3 — берём как основу,
  переписываем на свой backend-движок, когда понадобятся переменные, формы и статистика.
- Python-часть — там, где нужна настоящая логика и где Python объективно сильнее:
  правила, граф, исполнение, экспорт, API.
- Совместная работа в вебе — на WebSocket + Yjs/pycrdt, это отраслевой стандарт.
  В десктопе пришлось бы строить то же самое плюс синхронизацию клиента.

### 1.3. Библиотеки (Python)

| Задача | Выбор | Комментарий |
|---|---|---|
| API | `fastapi`, `uvicorn` | async, OpenAPI из коробки |
| Модели/валидация | `pydantic` v2 | схемы API и внутренние модели |
| БД | `sqlalchemy` 2, `alembic`, `asyncpg` | async ORM + миграции |
| BPMN XML | `lxml` (+ XSD `Semantic.xsd`/`BPMNDI.xsd`) | контроль пространств имён и DI |
| Парсер/исполнитель BPMN | `SpiffWorkflow` | парсит и исполняет BPMN 2.0; покрытие спецификации неполное → свой слой нормализации поверх |
| Граф и правила | `networkx` | достижимость, мёртвые концы, циклы, несвязанные узлы |
| Совместная работа | `pycrdt` (Yjs) + `redis` pub/sub | CRDT-документ на диаграмму |

| Тесты | `pytest`, `pytest-asyncio`, `hypothesis`, `schemathesis` | property-тесты на round-trip XML |
| Качество | `ruff`, `mypy --strict`, `pre-commit` | |

### 1.4. Альтернатива: 100% Python (PySide6, десктоп) — рассмотрена и отклонена

Если принципиально «всё на Python» — это делается и получается хорошо:

- `QGraphicsScene/QGraphicsView` — готовый движок для диаграмм: hit-testing, зум,
  выделение, drag, undo-стек (`QUndoStack`) уже есть;
- экспорт: `QSvgGenerator`, `QPdfWriter` — без headless-браузера;
- редактор и есть основной продукт, backend не нужен для MVP.

Цена: совместная работа превращается в «десктоп-клиент + сервер синхронизации»
(двойная работа), шаринг ссылки «посмотреть схему в браузере» требует отдельного
веб-рендера, а найм и поддержка десктопа дороже.

**Решение:** веб-вариант (§1.2). Пересматриваем, только если целевой заказчик —
изолированный контур без веб-инфраструктуры (см. §1.5, «когда десктоп всё же выигрывает»).

### 1.5. Веб или десктоп: почему веб

Аргументы в порядке весомости:

1. **Совместная работа — это и есть дифференциатор.** Bizagi Modeler бесплатен на десктопе,
   но бесплатная версия — строго на одного человека; редактирование вдвоём, комментарии,
   история версий появляются только в платной подписке и работают через облачный Process
   Library, то есть через браузер. То есть даже Bizagi, чтобы продать коллаборацию,
   был вынужден построить веб-часть. Начинать с десктопа — значит повторить этот путь
   в обратную сторону и дважды заплатить за одну фичу.
2. **Рынок уже браузерный.** ProcessMind, SAP Signavio, ARIS, Camunda Web Modeler,
   StormBPM, bpmn.io — все в браузере, все продают «моделируйте вместе». Десктоп
   сегодня — это либо бесплатная воронка (Bizagi Free, Camunda Desktop Modeler),
   либо инструмент под офлайн/air-gapped контур.
3. **Десктоп on PySide6 = двойная работа по коллаборации.** Нужен сервер синхронизации,
   и к нему отдельный клиент; в вебе это один WebSocket-канал. Плюс отдельная сборка
   под Windows/macOS/Linux, обновления, подпись кода, поддержка.
4. **Ссылка на просмотр.** «Кинь ссылку на схему» — базовое ожидание 2026 года.
   В десктопе это отдельный веб-рендер, то есть второй рендерер на поддержке.
5. **Нулевой порог входа.** Демо по ссылке без установки конвертирует в разы лучше,
   чем «скачай 200 МБ». Это прямо влияет на бесплатный тариф как воронку.
6. **Десктоп потом — дёшево.** Обёртка того же веб-редактора в Tauri/Electron даёт
   «приложение для Windows» за 1–2 недели: офлайн-кеш, локальные файлы, автообновление.
   Переписывание редактора на PySide6 — это месяцы и второй баг-трекер.

**Когда десктоп всё же выигрывает:** заказчик в закрытом контуре без веб-сервера;
работа с файлами на сетевых дисках как основной сценарий; схемы на 3000+ элементов
с локальным GPU; требование «данные не покидают машину» в жёсткой формулировке.
Если целевой клиент такой — меняем ADR-001 до спринта 1.1, дальше это стоит дорого.

## 2. Продуктовые рамки

### 2.1. Берём от Bizagi

- цветная схема: заливка/обводка/шрифт по элементу, темы, легенда, стили по умолчанию;
- широкий экспорт: SVG, PNG, PDF, BPMN 2.0 XML, JSON, DOCX-паспорт, CSV-реестр;
- «взаимодействие с элементами»: инспектор свойств, кастомные атрибуты, гиперссылки,
  вложения, комментарии, сворачивание подпроцессов, шаблоны.

### 2.2. Берём от StormBPM

- проверки схемы с переходом к проблемному элементу, severity, кастомные правила;
- прогон токена: play/pause/шаг, подсветка активных элементов, переменные, история,
  счётчики по элементам, поиск узких мест;
- совместная работа: присутствие, курсоры, комментарии с упоминаниями, роли,
  версии и восстановление, публичные ссылки на просмотр.

### 2.3. Сознательно НЕ делаем в v1 (бэклог, раздел 9)

BPMN-нотация целиком (только ~20 самых ходовых типов), DMN, интеграция с Camunda/Zeebe
как runtime, мобильный редактор, BI-дашборды, маркетплейс шаблонов, AI-генерация схем.

## 5. ЭТАП 1 — Редактор (детально)

Цель этапа: **пользователь рисует цветной процесс, сохраняет его, закрывает ноутбук,
возвращается — процесс на месте, и его можно выгрузить в 6 форматов.**

Демо-сценарий приёмки этапа (один и тот же прогоняем в конце каждого спринта):
> Создать диаграмму → нарисовать 3 пула с дорожками → 15 элементов с двумя шлюзами →
> раскрасить по ролям, добавить легенду → приложить ссылку и комментарий →
> экспортировать в SVG, PNG, PDF, BPMN XML → перезагрузить браузер → схема идентична.

### Спринт 1.1 — Модель данных и round-trip XML (23.11–06.12.2026)

Смысл: BPMN XML — источник истины. Если round-trip без потерь не работает сейчас,
дальше вся работа превращается в переделку.

- [x] 1.1.1 Pydantic-модели подмножества BPMN: `Process`, `LaneSet/Lane`, `StartEvent`,
      `EndEvent`, `UserTask`, `ServiceTask`, `ScriptTask`, `Task`, `ExclusiveGateway`,
      `ParallelGateway`, `InclusiveGateway`, `SequenceFlow`, `MessageFlow`,
      `BoundaryEvent`, `IntermediateCatch/ThrowEvent`, `SubProcess` (collapsed),
      `TextAnnotation`, `Group`, `Association`, `DataObject`
- [x] 1.1.2 Парсер BPMN XML → модель + сериализатор модель → XML; сохранение `BPMNDI`
      (координаты, размеры, waypoints, `isExpanded`) и неизвестных расширений
      (namespace-preserving, чтобы не терять чужие атрибуты)
- [x] 1.1.3 Property-тесты round-trip (`hypothesis`): случайная валидная схема →
      XML → модель → XML → побайтовое/семантическое равенство
- [x] 1.1.4 Схема БД: `diagram`, `diagram_version` (снапшот XML + метаданные),
      `diagram_acl`, `comment`, `attachment`; миграции Alembic
- [x] 1.1.5 API v1: `POST/GET/PATCH/DELETE /api/v1/diagrams`,
      `GET/PUT /api/v1/diagrams/{id}/bpmn`, `GET /api/v1/diagrams/{id}/versions`
- [x] 1.1.6 Фронт: загрузка XML с бэкенда и рендер через bpmn-js (read-only),
      зум/пан, мини-карта
- [x] 1.1.7 Валидация входящего XML по XSD (`lxml`), понятные 4xx-ошибки с номером строки
- [x] 1.1.8 Golden-тесты: 10 реальных BPMN-файлов (Bizagi, Camunda Modeler, bpmn-js)
      открываются без потерь

**Критерии приёмки:** 10 golden-файлов проходят round-trip; `GET/PUT` сохраняет схему;
покрытие парсера/сериализатора ≥ 80%; неизвестные атрибуты не теряются.

_Состояние на 12.11.2026: **выполнено**. 70 тестов бэкенда, покрытие `app/bpmn` — 93%
(парсер 88%, сериализатор 98%); `PUT` c чужим `If-Match` → 409; XML больше 5 МиБ → 413.
Найдено и исправлено по ходу (property- и браузерные тесты): DI-индекс был общим на
документ вместо «на плоскость»; пулы генерировались в отдельные плоскости, из-за чего
bpmn-js показывал только первый пул; `scriptFormat` должен быть атрибутом задачи, а не
`script`; у `association` и `textAnnotation` нет `name`; пустая строка ≠ отсутствие значения._

**Риск:** Bizagi-файлы содержат свои `extensions` — если теряем, ломается импорт.
Митигация: тест на сохранение «чужих» узлов уже в 1.1.2, а не потом.

## 6. Definition of Done (общий для всех задач)

Задача считается выполненной, если:
1. Код смержен в `main` через PR с ревью (или само-ревью + зелёный CI, если работаем один).
2. Есть тесты: юнит на логику, E2E на пользовательский сценарий (для UI-задач).
3. `ruff` + `mypy --strict` + `eslint` + `tsc --noEmit` зелёные.
4. Обновлён OpenAPI/документация, если менялся контракт API.
5. Задача проверена вручную на демо-стенде по сценарию из описания.
6. Нет новых `TODO` без ссылки на задачу в трекере.

**Definition of Ready:** у задачи есть ID, критерий приёмки в измеримом виде,
понятно, что не входит в скоуп, и нет открытых вопросов по дизайну (иначе — `[!]`).

## 8. Риски и допущения

| Риск | Влияние | Митигация |
|---|---|---|
| Потеря данных при round-trip чужих BPMN | Высокое | golden-тесты с реальными файлами уже в спринте 1.1 |
| bpmn-js не даёт нужной кастомизации стилей | Среднее | прототип кастомного модуля стилей в спринте 1.3 до основных работ; запасной путь — свой SVG-слой |
| Скоуп «как Bizagi» расползается | Высокое | рамки §2.3, любая новая фича — только через бэклог с оценкой |
| Один разработчик на весь стек | Среднее | приоритет вертикальных срезов; этапы 2 и 3 не зависят от совместной работы и могут идти первыми |
| Симуляция упирается в покрытие спецификации | Среднее | ограничить v1 «ходовым» подмножеством, остальное — ошибка с понятным сообщением |
| Путаница «модель vs исполнение» (Storm) | Низкое | статус диаграммы: draft / approved / archived |

Допущения: команда 1 backend (Python) + 1 frontend (TS) + 0.5 QA/UX; поставка — веб,
self-hosted через Docker; целевые пользователи — бизнес-аналитики и архитекторы,
не разработчики.
