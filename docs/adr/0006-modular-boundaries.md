# ADR-006. Границы ядра и модулей: модульный монолит

- **Статус:** принято
- **Дата:** 27.11.2026
- **Задача:** 4.0.1

## Контекст

После `v0.3` и редизайна 3.6 продукт должен получить модули wiki, задачи и чаты
(этап 5.5, `v0.6`). Модули нельзя начинать раньше пользователей и ACL
(4.1–4.2), иначе авторство и права придётся переделывать, а код ядра обрастёт
чужими таблицами и импортами. При этом микросервисы и отдельные БД на этом
шаге не нужны: команда маленькая, нагрузка одна, транзакции общие.

Сейчас в backend есть пакеты, которые уже ведут себя как отдельные области:
`app/bpmn` (модель, парсер, сериализация), `app/validation`,
`app/simulation`, `app/export`, `app/api/routes/comments.py`. Если не
зафиксировать границу до 4.1, «модульность» появится копированием таблиц и
прямыми `import` между фичами.

## Решение

Делаем **модульный монолит** с одним процессом, одним Postgres и одним Redis.
Код делится на **ядро** и **модули**, связь — только через контракты ядра и
события.

### Что где

| Сущность / область | Где | Обоснование |
|---|---|---|
| BPMN-модель, парсер, сериализатор, DI | ядро | без этого нет продукта |
| Диаграммы, версии, etag-сохранение | ядро | источник истины и история |
| Проверки схемы, конфиг правил, отчёты | ядро | часть редактора и сохранения |
| Симуляция, прогоны, тест-кейсы | ядро | часть редактора и версии |
| Экспорт (SVG/PNG/JSON/CSV/XLSX/DOCX/PDF) и очередь заданий | ядро | работает по диаграмме и версии |
| Комментарии к диаграмме и элементам | ядро | привязаны к холсту и версиям |
| Пользователи, сессии, ACL, роли | ядро | нужны всем модулям (4.1–4.2) |
| Файлы и вложения | ядро | общий контракт хранения (MinIO/S3) |
| Wiki-страницы и пространства | модуль `wiki` | не нужен редактору |
| Задачи, доски, назначения, связи с диаграммами | модуль `tasks` | прикладной сценарий поверх ядра |
| Чаты, каналы, сообщения, presence в чате | модуль `chat` | требует realtime 4.3–4.4 |
| Уведомления по модулям | модуль (по владельцу события) | выдаёт владелец сущности |

Комментарии остаются в ядре осознанно: они живут в инспекторе редактора, участвуют
в версиях и ссылаются на `element_id`. Вынос их в модуль заставил бы редактор
импортировать модуль, то есть нарушить правило зависимостей.

### Правило зависимостей

1. **Ядро не импортирует модули.** `app/core/**` и остальные пакеты ядра
   (`bpmn`, `validation`, `simulation`, `export`, `db`, `schemas`, `api/routes`
   ядра) не содержат `from app.modules...`.
2. **Модуль импортирует только контракты ядра** — `app/core/contracts`
   (протоколы сервисов, DTO, типы событий, базовые классы моделей). Импорт
   `app.modules.<other>` запрещён.
3. **Межмодульное взаимодействие** — события (`diagram.saved`,
   `comment.created`, `user.deleted`, …) через outbox/Redis (4.0.3) или вызов
   контракта ядра. Никаких прямых SQL-джойнов между таблицами модулей.
4. **Данные модуля принадлежат модулю:** таблицы с префиксом `<module>_`,
   миграции в его каталоге, ссылка на сущности ядра — только по ID
   (`diagram_id`, `user_id`), внешние ключи на чужие модульные таблицы запрещены.
5. **API:** ядро — `/api/v1/diagrams`, `/comments`, `/health`; модуль —
   `/api/v1/<module>/...`. Добавление модуля не меняет существующие роуты.
6. **Включение модуля:** `MODULES_ENABLED=wiki,tasks,chat`. Выключенный модуль
   не регистрирует роуты, задачи и подписки; таблицы при этом остаются в БД,
   чтобы миграции не зависели от окружения.
7. **Frontend:** модуль — `frontend/src/modules/<name>/` с ленивыми маршрутами
   и своим API-клиентом; общие компоненты — из `src/components`, обратный импорт
   (`компонент → модуль`) запрещён.

### Что не делаем

- микросервисы, отдельные БД и брокер сообщений на этом этапе;
- общие таблицы «на будущее» и универсальный `entity_type/entity_id` для всего;
- импорт модулей из ядра «временно, чтобы быстрее» — это и есть главный риск;
- перенос комментариев, проверок и симуляции в модули.

## Последствия

- 4.0.2–4.0.5 раскладывают backend на `app/core/**` и `app/modules/**`,
  добавляют реестр модулей и frontend-каркас без изменения поведения.
- 4.0.6 закрепляет правило автоматически: import-linter и контрактные тесты
  (ядро без `app.modules`, модуль без соседей), плюс тест, что выключенный
  модуль не регистрирует роуты.
- Если модуль позже станет отдельным сервисом, контракты и события уже будут
  готовы; переезд не потребует менять ядро.
- Цена — дисциплина импортов и префиксы таблиц; выгода — модули можно включать
  и выключать, а ядро остаётся компактным.
