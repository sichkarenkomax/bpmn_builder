# ADR-001. Форма поставки и стек

- **Статус:** принято
- **Дата:** 12.11.2026
- **Задача:** 0.4

## Контекст

Продукт должен закрыть три требования: богатое визуальное моделирование (Bizagi),
проверки и прогон токена (StormBPM), совместная работа (StormBPM). Совместное
редактирование — ключевой дифференциатор: бесплатный Bizagi Modeler работает на одного,
а коллаборация у Bizagi доступна только в платной подписке через облачный Process Library.

Рассматривались два пути: веб-приложение и десктоп на PySide6 (100% Python).

## Решение

Делаем **веб-приложение**:

- backend — Python 3.12 + FastAPI (бизнес-логика, парсинг BPMN, правила, симуляция, экспорт);
- frontend — React + TypeScript, ядро редактора bpmn-js (см. ADR-002);
- хранилище — PostgreSQL, Redis (presence/pub-sub), S3-совместимое (MinIO) для вложений;
- поставка — Docker Compose локально, далее образы + Helm для on-prem.

Десктоп-приложение не пишем. При необходимости (офлайн, локальные файлы) на этапе 6
делается обёртка Tauri вокруг того же веб-редактора.

## Почему не PySide6

1. Коллаборация превращается в «сервер синхронизации + отдельный клиент» вместо одного
   WebSocket-канала, и требует второго рендерера для ссылок «посмотреть в браузере».
2. Нет нулевого порога входа: демо по ссылке конвертирует лучше, чем установка 200 МБ.
3. Сборка, обновления и поддержка под три ОС — постоянные расходы, которых у веба нет.
4. Qt даёт отличный холст (`QGraphicsScene`), но это единственное его преимущество здесь.

## Последствия

- Нужен второй язык (TypeScript) — принято осознанно: он нужен только для UI-слоя.
- Экспорт PDF/DOCX выполняется на сервере — одинаково для всех клиентов.
- Офлайн-режим появится только с Tauri-оболочкой (этап 6), не раньше.

## Когда пересмотреть

Заказчик в закрытом контуре без веб-сервера; работа с сетевыми дисками как основной
сценарий; требование «данные не покидают машину». Тогда PySide6-клиент обсуждается
заново, но только после того, как определены API и модель документа.
